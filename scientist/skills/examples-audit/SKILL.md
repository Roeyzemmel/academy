# Standard-examples audit

A definition that has never been evaluated on an example is a definition nobody has
read carefully. This audit makes sure every definition has such a test, or a recorded
reason why it cannot have one.

`$ARGUMENTS`: the instance whose definitions are audited (`author@<paper>` or
`researcher@<domain>`), a list of definition ids, or a ticket id. Budget
(`${CLAUDE_PLUGIN_ROOT}/../academy/references/budget.md`): one experimenter dispatch
per run, briefed with the whole list; the rest waits for the next invocation.

## The standard examples

They are the domain pack's, not this skill's: `domain_get(name=<domain>,
file="examples.md")`. Every definition test reports its value on **every** example
listed there, and the pack says what each example catches. Pay attention to the
example the pack marks as discriminating (one that a too-narrow definition must
visibly refuse): a test that returns a happy answer there has found a bug in the
definition or in the script, which is exactly what the audit is for.

## Procedure

1. **Enumerate the definitions** of the audited instance from its registry:
   `claims_list(ns=<its ns>, kind="definition")`, or for a paper its generated
   statements view (named in that home's `academy.json`). Include remarks that
   introduce a term later used as defined. Say which source you used.
2. **Check what exists.** For each definition, the lab claims bearing on it:
   `claims_deps(id=<definition id>, reverse=true)`, then `claims_show` on each lab
   claim and `queue_status(label=...)` for its jobs. A settled lab claim needs
   nothing. An open one is reported with its jobs (pending, running, failed,
   parked, none). Re-queue only a failed job whose cause is fixed; never un-park a
   job Roey parked.
3. **Dispatch one `experimenter`** with the list of untested definitions:

   > For each definition, write a definition test in the lab's experiments that
   > evaluates the definition, exactly as its owner states it (quote it with its
   > id), on each standard example of the pack's `examples.md`, and reports the value
   > plus pass/fail against what the owner says the value should be. The header
   > states the reading of the definition in words and names every place the reading
   > was a choice. Add the drop-one variants: each hypothesis removed, the same test.
   > Record one lab claim per definition (`claims_new`, `bears_on:` the definition's
   > id, header `Kind: verify` or `measure`). Queue on the run profile; never compute
   > locally. Return after the first definition if the list is long.

4. **Not computable** is a finding, not a failure: a definition quantifying over all
   of an infinite family, over a limit object, or over infinitely many parameters.
   It gets a lab claim (`claims_new`, status `open`) whose title gives **a one-line
   reason** saying precisely what is not finite about it, and a proposal
   (`claims_propose_status`) that the claim-keeper set its lifecycle to `dropped`. Where a *necessary condition* is
   computable, test that instead and say in the claim that a failure is a lead and a
   pass is not a verification.

## Constraints

- No edits to the audited instance's files. An outcome that contradicts a definition
  becomes a ticket to that instance (`tickets_create`, kind `question`, refs = the
  definition and the lab claim), never an edit. A question to an Author instance goes
  to the Researcher with `final_to: author`; a question to a Researcher is filed
  to it directly.
- Generated views are regenerated by their owners, never edited.
- Code and results live in the lab. No `git add`, `commit`, `stash`, `checkout` or
  `reset` in another home.

## Report

A table: definition id, lab status before, action (claim added / queued / already
done / not computable), job id. Then the not-computable definitions with their
reasons, the definitions that now have a test pending, and any definition whose
owner-stated value the experimenter could not determine: that last class is an
ambiguity in the definition itself and the most valuable thing this audit finds. It
goes back to the owner as a `question` ticket. Never ask questions from a subagent.
